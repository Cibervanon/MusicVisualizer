01 · Visión general

Qué es y qué no es

Lumen Studio es una aplicación de escritorio-servidor que corre en 127.0.0.1. El usuario sube audio y vídeo, elige un fragmento, un formato y estilos de montaje, y recibe clips MP4 montados sobre los beats reales de la música.

♪

Análisis musical real

BPM, beats, downbeats, secciones, eventos y envolventes por banda (kick, bass, snare, hat) calculados con librosa. Sin beats inventados: si el detector falla, se usa una rejilla declarada como fallback.

▦

Análisis visual medido

PySceneDetect localiza escenas; OpenCV mide movimiento, nitidez, brillo, estabilidad, color y saliencia. El planificador usa esas métricas para elegir planos.

✂

EDL reproducible

Cada clip es una lista de decisiones de edición (EDL) con IDs estables. Se puede reabrir, editar, previsualizar y volver a renderizar sin perder el montaje.

▶

Preview y final con el mismo EDL

La preview no es una simulación: se renderiza con FFmpeg a menor resolución y preset rápido. La única diferencia con el render final es la resolución y la codificación.

✓

Validación objetiva

Después de cada render, ffprobe comprueba duración, resolución, fps, codecs, pistas, decodificación completa, sincronía A/V, keyframes, perfil H.264 y espacio de color.

◎

Honestidad de estado

El progreso viene de -progress pipe:1 de FFmpeg. No hay barras simuladas, ni checkmarks decorativos, ni estados de éxito sin archivo validado en disco.

Principios de diseño

  • Local-first: los datos viven en projects/<id>/ como JSON y MP4. No hay base de datos ni migraciones.
  • Privacidad: el audio, el vídeo y las letras nunca salen de la máquina. La importación por URL es opcional y explícita.
  • Un solo EDL: preview, render final y editor leen y escriben el mismo documento persistido.
  • Corrección antes que features: los estados terminales, los límites de duración y las rutas de archivo se validan en el backend, no solo en la UI.
  • Accesibilidad: UI en español, navegación por teclado en la timeline, landmarks, skip link, foco atrapado en modales y regiones aria-live.

Alcance del documento. Describe el código tal como está hoy, incluyendo limitaciones conocidas. Las secciones de testing y estado citan comandos ejecutados y sus resultados reales.

02 · Arquitectura

Cliente y servidor en la misma máquina

El frontend es una SPA de React + TypeScript servida por Vite en desarrollo. El backend es FastAPI y expone una API REST con Server-Sent Events para el progreso. En producción, el propio FastAPI sirve el dist/ compilado con fallback SPA.

Frontend · React 18 + TypeScript + Zustand

Cinco pantallas (Setup, Customize, Generating, Results, Editor) y componentes de UI reutilizables. Las llamadas pasan por validatedApi.ts, que valida respuestas con Zod.

API · FastAPI + Pydantic

Routers por dominio: proyecto, subida, análisis, clips, render, jobs, letras, archivos y sistema. Errores normalizados con código y detalle.

Núcleo · analysis / editing / media / quality / lyrics / jobs

Funciones puras y servicios con estado explícito. El render se ejecuta como subproceso de FFmpeg, nunca en el event loop.

Almacenamiento · sistema de archivos

Un directorio por proyecto con JSON legibles y archivos MP4. Las rutas se validan con safe_join para impedir traversal.

Estructura de un proyecto

projects/<project_id>/
├── project.json          # metadatos, audio, vídeo, config, edits, renders, letras
├── source/               # audio y vídeo originales subidos
├── analysis/             # análisis de audio y biblioteca de escenas (JSON)
├── master/               # vídeo normalizado y cacheado por hash de parámetros
├── edits/                # EDLs guardados (uno por clip)
├── renders/              # <render_id>.mp4 + miniaturas
├── lyrics/               # letras persistidas y ASS generado
├── thumbs/               # miniaturas de vídeo
└── tmp/                  # grafos de filtros y archivos temporales

03 · Flujo de trabajo

De la canción al MP4 en cinco pasos

Setup

Subida de audio y vídeo (o importación por URL autorizada), selección del fragmento con inicio y fin, y preflight de capacidades del sistema.

Análisis

El audio se decodifica a mono 22 050 Hz y se analiza con librosa. El vídeo se normaliza a un máster único (formato, resolución y fps fijos) y se analiza por escenas.

Personalización

Formato (9:16, 1:1, 16:9, 4:5), resolución, fps, calidad, encoder, número de clips, estilos y pesos de planificación. Las letras se pueden importar o transcribir.

Generación

Un job analiza, planifica, renderiza y valida cada clip. El progreso se emite por SSE y la cancelación detiene FFmpeg de verdad.

Resultados y edición

Los MP4 se reproducen, descargan individualmente o en ZIP. El editor permite ajustar cortes, efectos y letras y volver a renderizar preview o final.

Un único EDL por clip. El editor guarda el EDL en edits/. Tanto la preview como el render final leen ese archivo persistido; si hay cambios sin guardar, la UI lo advierte antes de renderizar.

04 · Análisis de audio

Beats, downbeats y estructura

El análisis se ejecuta offline con librosa sobre el fragmento seleccionado. El resultado se cachea por clave de audio y se reutiliza entre clips y estilos.

Pipeline

y, sr = librosa.load(mono_path, sr=22050, mono=True)

onset_env = librosa.onset.onset_strength(y=y, sr=sr, hop_length=512)
tempo, beats = librosa.beat.beat_track(
    onset_envelope=onset_env, sr=sr, hop_length=512, units="time"
)
onsets = librosa.onset.onset_detect(
    onset_envelope=onset_env, sr=sr, hop_length=512, units="time"
)

rms  = librosa.feature.rms(y=y, hop_length=512)[0]
stft = np.abs(librosa.stft(y, n_fft=2048, hop_length=512))
# Bandas: kick 40–120 Hz · bass 60–250 Hz · snare 200–4000 Hz · hat 6000–11000 Hz
flux = np.sqrt(np.sum(np.diff(stft, axis=1) ** 2, axis=0))

Fuerza de beat: normalización vectorial

Defecto corregido. La fuerza se normalizaba beat a beat, de modo que cada valor acababa en 1.0: la jerarquía desaparecía y los downbeats se detectaban mal.

Solución. Se calcula la fuerza bruta de todos los beats y se normaliza una sola vez con el percentil 99: strengths = _norm(np.array(raw), 99.0). La jerarquía se conserva y los acentos son comparables.

Downbeats y confianza

Se prueban las cuatro fases de un compás 4/4 y se elige la que maximiza la suma de acentos. La confianza combina la separación entre la mejor y la segunda fase con el soporte disponible: 

confidence = (best - second) / best * min(1, n_beats / 8)

Con pocos beats o fases empatadas la confianza baja y el planificador deja de tratar esos beats como downbeats. El valor se expone como tempo.downbeat_confidence.

Contrato de salida

Máster normalizado

Un único archivo por combinación de fuente, formato, resolución y fps. El nombre incluye dimensiones y fps (por ejemplo master_404x720_30.mp4 para 9:16 a 720p y 30 fps). Se reutiliza entre estilos y clips, y se invalida si cambia el hash de la fuente.

06 · Planificación EDL

Convertir beats y escenas en un montaje

El planificador recibe el análisis de audio, la biblioteca de escenas y la configuración de estilo, y devuelve un EDL con segmentos ordenados. Cada segmento sabe qué trozo del máster usar y en qué punto de la timeline cae.

Scoring multi-criterio

Cada corte candidato se puntúa con pesos configurables. Los valores por defecto son:

La diversidad penaliza reutilizar la misma escena; la semilla y el índice de versión hacen que dos clips del mismo estilo no sean idénticos sin volverse impredecibles.

Invariantes que se validan

  • La duración del EDL es la suma exacta de las duraciones de sus segmentos.
  • Cada segmento tiene id único y estable, no un índice posicional.
  • source_duration ≥ duration y los límites caen dentro del máster.
  • Duración mínima de segmento: 0.12 s.
  • Un EDL cuya duración no coincide con la suma se rechaza en el backend.
  • El montaje no puede superar la duración del fragmento de audio.

Ripple correcto. Al acortar un segmento, la timeline se recompone y la duración total baja. El límite para alargar no es la duración actual del EDL sino la duración del fragmento, de modo que se puede recuperar espacio recortado.

07 · Render

Un proceso FFmpeg por clip

El render construye un grafo de filtros completo y lo ejecuta en una sola invocación de FFmpeg. Esto evita archivos intermedios y permite un progreso continuo y cancelable.

Grafo de filtros

  • Entradas: una instancia del máster por segmento, con -ss y -t para el seek, más el audio del fragmento.
  • Por segmento: trim exacto, setpts, fps, scale con lanczos, setsar=1 y settb=AVTB.
  • Unión: concat para cortes y xfade para crossfades con offset calculado. El estilo flash intercala fades a blanco.
  • Duración exacta: tpad con clonación del último frame y trim final a la duración del EDL.
  • Efectos: eq (grade), unsharp, vignette, noise, gblur + blend=screen y rgbashift, solo si el estilo los permite.
  • Audio: atrim, asetpts, volumen y loudnorm=I=-14:TP=-1.5:LRA=11.
  • Salida: H.264 High Profile, yuv420p, AAC 48 kHz, +faststart, -shortest y GOP de 2 s (-g fps×2) para seeking y preview fluida.

FFmpeg 9. El grafo se pasa con -/filter_complex <archivo> mediante filter_graph_input(), evitando límites de longitud de línea de comandos en montajes con muchos segmentos.

Frescura del render

Un render se considera desactualizado cuando edit.edited_at es posterior a render.created_at. El editor muestra el badge correspondiente y avisa de que la preview no incluye los cambios pendientes. Al guardar, el backend revalida el EDL completo.

Limitación conocida. El playhead de la timeline es estado de React y no usa requestAnimationFrame; con montajes muy largos puede haber más renders de los necesarios. Está en el roadmap, no se presenta como resuelto.

10 · Jobs

Progreso real y cancelación definitiva

Los trabajos largos (análisis, generación, render) se ejecutan como jobs con estado en memoria, progreso emitido por SSE y cancelación cooperativa que termina el proceso de FFmpeg.

Máquina de estados

TERMINAL = {"done", "error", "cancelled"}

queued     → running
running    → cancelling      (si se solicita cancelación)
cancelling → cancelled       (el runner confirma)
running    → done            (éxito, tras validar el archivo)
running    → error           (fallo con código y detalle)

cancelled es terminal: no puede volver a running, queued ni done.

Cancelación

async def cancel(job_id: str):
    job = await store.get(job_id)
    if job["status"] in TERMINAL:
        return job
    job["status"] = "cancelling"
    job["message"] = "Cancelando…"
    event = self._events.get(job_id)
    if event is not None:
        event.set()          # despierta al runner
    return job

El runner comprueba el evento en los puntos de control y en cada actualización de progreso. Al cancelarse, se termina el subproceso, se limpian los temporales y el job queda en cancelled. Ninguna transición posterior puede sobrescribirlo.

Progreso desde FFmpeg

cmd = [FFMPEG, "-hide_banner", "-y", "-nostdin", "-progress", "pipe:1", "-nostats", *args]

while True:
    line = await proc.stdout.readline()
    if not line:
        break
    if line.startswith(b"out_time_ms="):
        ms = int(line.split(b"=")[1])
        await on_progress(min(1.0, ms / 1000 / duration))

El mismo callback alimenta el estado del job y la respuesta SSE. Cuando no hay cambios se envían keep-alives para mantener viva la conexión.

En memoria. Los jobs se pierden al reiniciar el backend. Los resultados ya renderizados permanecen en disco y el proyecto se puede recargar; el historial de jobs no.

15 · CI/CD

GitHub Actions

El workflow .github/workflows/ci.yml se ejecuta en pull requests y en pushes a main. Cada job usa la misma versión de Python y Node que el desarrollo.

JobQué ejecuta
frontend-lintnpm run lint y tsc --noEmit
frontend-testnpm test (13 tests de edición)
frontend-buildnpm run build y artefacto dist
backend-lintruff check . y mypy app/
backend-testComprueba FFmpeg y ejecuta los 22 tests
security-auditnpm audit --audit-level=high y pip-audit
bundle-sizeBuild y presupuesto gzip: JS < 180 KB, CSS < 20 KB
ci-summaryAgrega resultados y falla si algún job falla

Dependabot está configurado para npm, pip y GitHub Actions con actualizaciones semanales o mensuales según el ecosistema. El tamaño actual del bundle es de 483 KB sin comprimir y 142 KB gzip, dentro del presupuesto.

Estado de CI. Los comandos del workflow se han ejecutado en local con las mismas versiones y pasan. La ejecución remota en GitHub Actions queda pendiente de confirmación tras el push.

Limitaciones conocidas

  • No hay autenticación: el servidor está pensado para 127.0.0.1, no para exposición pública.
  • Los jobs viven en memoria y se pierden al reiniciar el backend.
  • La transcripción de letras requiere instalar requirements-optional.txt.
  • La UI no tiene E2E automatizado; la verificación de flujos es manual.
  • La cobertura de tests no se mide ni se impone como umbral.

Regla del proyecto. Si una función no renderiza, no valida o no persiste, no se muestra como si lo hiciera. Los controles decorativos y los estados de éxito inventados se consideran defectos.
